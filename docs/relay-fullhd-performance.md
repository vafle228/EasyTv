# RelayVSR до Full HD: проверка 13.11.2026

RTX 5060 Ti 16 ГБ, Windows/Docker, исходный RelayVSR e856773350f53036d825404c9ea9228e6dffadca,
BF16, одна пара моделей в GPU. Приложение ограничивает PyTorch 85% памяти устройства.

## Интеграция

Через отдельный настоящий сервер EasyTv и worker обработаны синтетические MP4 со звуком,
24 FPS, 48 кадров / 2 секунды. Исходники 256×144, 854×480 и 1280×720 дали 1920×1080.
Проверены H.264, все 48 кадров, номинальные 24 FPS, AAC и HTTP Range/DLNA через EasyTv.
Первые 144p заняли 88,72 с с загрузкой весов и прогревом ядер; следующие 480p и 720p —
8,74 и 8,69 с. Пик общей занятой VRAM, включая рабочий стол, 15 382 MiB (~15,0 GiB).
Это короткие прогоны, не гарантия времени длинного фильма.

Исходник 1920×1080 вернул оригинал с пояснением за 0,047 с, без задания. Отдельно проверен
HTTP-источник 1080p: worker вернул 409 до запуска процесса инференса. В браузере подтверждены
оригинал для Full HD, пояснение и воспроизведение улучшенного 144p в 1920×1080. Реальный ТВ
в этой задаче не проверялся; команды ТВ, очередь и сохранение оригинала покрыты сценарными тестами.

## Поиск ускорения

Фрагмент фильма: 852×480, 23,976 FPS, 96 кадров (4,004 с), вход модели 479×270,
выход 1916×1080. Один процесс с одними весами, сначала полный прогрев, затем отдельный
инференс каждого варианта без повторного использования готового результата. Загрузка весов
заняла 62,11 с; прогрев — 32,24 с. Они исключены из таблицы.

| Вариант | Время на 4,004 с видео | FPS | Секунд обработки на секунду видео |
| --- | ---: | ---: | ---: |
| Обычное окно 16 | 15,53 с | 6,18 | 3,88 |
| Окно 16 + cuDNN autotune | 15,62 с | 6,15 | 3,90 |
| Окно 32 + autotune | 12,66 с | 7,58 | 3,16 |
| Окно 64 + autotune | 10,74 с | 8,94 | 2,68 |

Окно 64 дало +45% FPS / −31% времени, но ещё не 12 FPS для цели 1:2 на видео 24 FPS.
Кадры видео не пропускаются. Меняется частота дорогих опорных кадров Wan: окна 16/32/64
соответствуют интервалам 15/31/63 кадра. Это меняет результат модели, особенно на движении
и смене плана. Один просмотренный стоп-кадр не выявил грубого расхождения; временная
стабильность и качество на разных сценах не проверены. **В приложении остаётся окно 16**.
Autotune по этому замеру выигрыша не дал и тоже не включён.

В базовом прогоне GPU-этап Wan занял 6,31 с, Flash — 6,61 с. При окне 64 Wan снизился
до 2,12 с, Flash остался 6,34 с. Поэтому дальнейшее увеличение интервала не устраняет
покадровую стоимость Flash. Замер `yield_to_encoder_s` включает ожидание GPU при копировании
кадра в CPU, его нельзя складывать с CUDA-этапами или считать чистой стоимостью кодирования.
Общая занятая VRAM 14,9–15,1 GiB; расширение окна не решает задачу освобождения памяти.

Скрипт воспроизведения: [relay_fullhd_benchmark.py](../experiments/relay_fullhd_benchmark.py),
[сырые численные результаты](../experiments/relay-fullhd-results.json). Запуск в существующем
образе worker, с каталогами входа и результата, смонтированными как `/input` и `/results`:

```sh
python /experiment/relay_fullhd_benchmark.py /input/clip.mp4 /results
```

Перед запуском остановить остальные GPU-worker, чтобы не загружать вторую копию весов.
Видеофрагменты, результаты с кадрами фильма, пользовательские URL и веса в репозиторий не входят.

## Следующие варианты

1. Проверить компиляцию именно RelayVSR, прежде всего покадрового Flash. Это пока гипотеза
   ускорения, измерения torch.compile для SeedVR2 к RelayVSR не относятся.
2. Рассмотреть интеграцию LightX2V: его [официальная инструкция RelayVSR](https://github.com/ModelTC/LightX2V/blob/main/scripts/relayvsr/README.md)
   включает компиляцию и прогрев по умолчанию, resident-server и собственные веса native ×2.
   Произвольный коэффициент ниже native масштаба там реализован финальным уменьшением после
   native-инференса. Это не бесплатное уменьшение вычислений текущей модели ×4. На этой GPU
   LightX2V и его ×2-вариант не запускались; переход требует отдельных зависимостей и согласования.

Достигать 1:1 снижением FPS исходника в этом эксперименте не пробовали: это изменило бы плавность видео.
