# EasyTv: инструкции для работы над проектом

## Назначение и границы

EasyTv — домашний агрегатор источников контента для просмотра на телевизоре, независимо от ограничений его встроенных приложений и провайдеров. «Прошивание» здесь означает расширение возможностей через локальный сервер, а не изменение прошивки телевизора.

Основной сценарий: с телефона найти контент, сохранить и запустить на домашнем телевизоре. Загрузка файлов с компьютера — дополнительный сценарий для продвинутых пользователей. Браузерное воспроизведение поддерживается, но главная цель — телевизор.

Сервер и управляющие клиенты находятся в домашней локальной сети. Публичный доступ и эксплуатация вне локальной сети не входят в проект. Интернет нужен серверу для внешних источников. Выделенного домашнего сервера пока нет; текущий запуск выполняется скриптами на компьютере пользователя.

Пользователь подтвердил полный цикл загрузки локального видео через сайт и просмотра на телевизоре. Это не подтверждение совместимости со всеми телевизорами или работоспособности всех внешних провайдеров.

## Стек

Бэкенд: Python >=3.11, FastAPI, Uvicorn, Pydantic (через FastAPI), httpx, python-multipart, yt-dlp; тесты — pytest. Точные ограничения версий находятся в `backend/pyproject.toml`.

Фронтенд: React 19, TypeScript 5.8, Vite 6, обычный CSS и собственные компоненты. Нет отдельной библиотеки маршрутизации или глобального состояния: используются собственный router, React hooks и context. Зависимости описаны в `frontend/package.json`.

Запуск: Docker Compose и `run.sh`; Windows-обёртки `run.cmd` и `run.ps1` вызывают этот же скрипт через Git for Windows. Возможен native-запуск с Python и Node.js. ffmpeg используется для обработки скачиваемого видео; его наличие само по себе не означает поддержку всех потоковых форматов.

## Архитектура бэкенда

Следовать существующей архитектуре портов и адаптеров:

- `core/models.py`, `errors.py` — предметные модели и ошибки.
- `core/ports.py` — интерфейсы поиска и управления ТВ, хранилищ, загрузчиков, каталога и системных сервисов.
- `core/services.py` — поиск ТВ, библиотека, воспроизведение; `core/catalog.py` — каталог и сохранённые тайтлы.
- `infrastructure/` — SSDP, UPnP/SOAP AVTransport, yt-dlp, загрузка потоков, файловое хранилище, JSON-репозитории и animego.
- `api/` — FastAPI-роуты, DTO, ошибки HTTP, отдача медиа, прокси потоков и хостинг SPA.
- `container.py` — сборка зависимостей; `config.py` — настройки окружения.

Ядро зависит от портов, не от FastAPI и конкретных сетевых адаптеров. Новые источники подключать через соответствующие порты, не встраивать парсинг сайтов в HTTP-роуты или React-компоненты. Бизнес-правила держать в сценариях ядра, преобразование в HTTP — в API.

Метаданные хранятся в JSON, видео — в файлах в `data/`; реляционной БД нет. Существующие репозитории используют память процесса и запись файлов: не считать их готовыми к нескольким серверным процессам или распределённому запуску. Не удалять пользовательскую библиотеку ради тестов.

## Архитектура фронтенда и взаимодействие

- `App.tsx`, `router.tsx`, `routes.ts` — композиция экранов и клиентская навигация.
- `pages/` — рабочие экраны; `components/` — общие компоненты.
- `api.ts` — клиент HTTP; `types.ts` — вручную поддерживаемые типы контракта.
- `hooks.ts` — загрузка и периодическое обновление данных; `nowPlaying.tsx` — состояние воспроизведения; `theme.ts` — тема.
- `demo/` — демонстрационные разделы, не готовые серверные функции.
- `styles.css` — действующий источник токенов и стилей.

Клиент посылает JSON-запросы на `/api`; загрузка файла — multipart. Данные обновляются опросом, не через WebSocket. В разработке Vite на :5173 проксирует `/api`, `/media`, `/stream` на :8080. В собранном приложении FastAPI раздаёт SPA и API с одного адреса.

При показе видео сервер передаёт телевизору доступный по LAN HTTP-адрес через UPnP AVTransport. Телевизор сам читает видео с `/media` или `/stream`; телефон управляет процессом, но не ретранслирует видео. Сохранять поддержку Range и DLNA-заголовков. Подробности контракта — в `docs/api-contract.md`.

## Текущие ограничения и планы

- Нужен телевизор с совместимым DLNA/AVTransport; поддержка конкретных кодеков зависит от устройства.
- SSDP multicast может не проходить из Docker: используются поиск с хоста, известные адреса и сканирование подсети. Телевизору должен быть доступен адрес сервера и порт в локальной сети.
- Внешние сайты меняются; ссылки на видео могут истекать и зависеть от IP. Сервер получает и проксирует ссылки. Фикстуры проверяют сохранённые ответы, а не текущее состояние сайта.
- Текущий каталог выбирает MP4; HLS-only источники не поддерживаются текущим сценарием воспроизведения.
- Библиотека и кинотеатр сейчас общие. `watched` пополняется при начале серии, а не по факту полного просмотра. Точного сохранения позиции для продолжения пока нет.
- Планируются пользователи без обязательных аккаунтов и паролей, персональная история, «хочу посмотреть» и продолжение с места остановки. Идентификация по устройству или свободный выбор профиля ещё не определены; не принимать решение самостоятельно.
- Торренты и прямой эфир — будущие функции, существующие демо не считать реализацией.
- CI/CD и автоматическая доставка — планы. Среда будущего сервера и политика обновления во время просмотра ещё не определены.

## Процесс разработки

1. Прочитать эти инструкции и `TASKS.md`, уточнить критерии выбранной задачи. Проверить актуальную базовую ветку, состояние репозитория и чужие изменения.
2. Под каждую задачу использовать отдельный worktree и осмысленную ветку `codex/<task>`. Не смешивать задачи и не переносить чужие незакоммиченные изменения. Создание worktree не означает разрешение запускать дополнительных агентов без отдельного указания.
3. Сохранять архитектуру, использовать классические паттерны по необходимости, поддерживать простой и чистый код. Не проводить попутные масштабные рефакторинги.
4. Добавление зависимости предварительно согласовывать с пользователем: объяснить назначение, необходимость и возможную альтернативу без зависимости.
5. Покрывать новую логику и исправления содержательными тестами поведения. Использовать фейковые порты для сценариев, фикстуры — для парсеров. Не требовать реальный телевизор или внешнюю сеть для обычных тестов.
6. Запустить тесты. Для бэкенда: из `backend` выполнить `python -m pytest` в окружении с установленным `.[test]`; Docker-вариант — `run.cmd test` или `./run.sh test`. Доступные команды фронта находятся в `frontend/package.json`. Ручная проверка на телевизоре не является обязательным условием каждой задачи; не выдавать автоматические проверки за живую проверку.
7. Делать небольшие логические коммиты с сообщениями на русском. Коммиты и push разрешены без отдельного запроса. Открыть pull request (MR) в GitHub с русским описанием результата и проведённых проверок.
8. Если CI настроен, дождаться его завершения, разобраться в падениях, исправить связанные с задачей ошибки и повторить проверки. Не отключать проверки ради зелёного статуса. Внешние блокировки и несвязанные падения описать явно. Если CI нет, не сообщать, что он прошёл.
9. Дождаться явного одобрения пользователя на слияние. Пользователь либо сливает PR сам, либо поручает это агенту. Зелёный CI не заменяет одобрение.
10. После подтверждённого слияния убрать рабочую ветку локально и на origin, если она ещё существует, и удалить/архивировать worktree. Сначала проверить, что там нет несохранённой работы; не применять принудительное удаление к чужим изменениям.

Функция готова, когда она подключена к реальному бэкенду и проверена тестами. Заглушки и демо явно обозначать. В отчёте указывать результат, проверки и оставшиеся ограничения. Не публиковать `.env`, пользовательские данные или секреты.

Для публикации использовать уже авторизованный GitHub CLI (`gh auth status --active --hostname github.com`, затем `gh pr create --repo vafle228/EasyTv --base main --head <ветка> --title "<заголовок>" --body-file <файл>`) или форму GitHub в браузере с активным входом. При отсутствии доступа сообщить об этом и дать ссылку на форму PR. Авторизацию оставлять штатному клиенту GitHub, без извлечения токенов из Git Credential Manager.
